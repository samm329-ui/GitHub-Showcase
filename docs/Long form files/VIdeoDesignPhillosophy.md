# OCTAVIUS — LONG-FORM GITHUB VIDEO PRODUCTION
## Creative Direction, Editing Specification & Implementation Instructions

**Document type:** Production and engineering instruction  
**Format:** YouTube landscape video, 16:9  
**Target duration:** Approximately 5 minutes  
**Resolution:** 1920 × 1080  
**Frame rate:** 30 FPS  
**Episode structure:** Five GitHub repositories  
**Creative identity:** Mascot-led technology showcase with modern social-media-style editing  
**Primary requirement:** Reproduce the exact visual and audio identity described in this specification consistently across every episode.

---

# 1. OBJECTIVE

Build a production-ready Long-form GitHub video-generation pipeline.

The final video must feel like a carefully edited technology showcase created by a professional video editor.

It must combine:

- A memorable mascot-led opening.
- A short, catchy narration hook.
- Strong, coordinated sound design.
- Animated repository introduction cards.
- Authentic GitHub website recordings.
- Authentic README and source-code demonstrations.
- Purposeful zooming, panning and scrolling.
- Selective, modern kinetic captions.
- Recurring mascot appearances with different screen positions.
- Short explanatory callouts.
- Consistent background music.
- A mascot-led closing sequence.

The editing style should have the energy of modern Instagram Reels, while retaining the clarity and visual space of a professional landscape video.

**This must not become a generic documentary, static slideshow, automated PowerPoint or basic screen recording.**

The video must look deliberately edited. Every animation, caption, sound effect and camera movement must have an editorial purpose.

## Non-negotiable creative principles

1. The mascot establishes the personality of the series.
2. Real GitHub footage provides the information.
3. Narration explains the project.
4. Captions reinforce the most important spoken information.
5. Callouts emphasize important points rather than repeating entire sentences.
6. Sound design reinforces visual events.
7. Camera movement directs the viewer's attention.
8. Hard cuts are the default editing transition.
9. The same visual identity is maintained throughout all five repositories.
10. No visual element should be added merely to make the screen look busy.

# 2. MASTER VIDEO STRUCTURE

The episode must follow this exact sequence.

| Sequence | Content |
|---|---|
| 01 | Mascot appears suddenly |
| 02 | Short introductory narration and animated hook captions |
| 03 | Mascot callout: "Let's dig in" |
| 04 | Repository 01 introduction card |
| 05 | Actual Repository 01 screen recording |
| 06 | Mascot appearances and explanatory callouts |
| 07 | README and code demonstrations |
| 08 | Repository 01 conclusion |
| 09 | Repository 02 card and presentation |
| 10 | Repeat the same editorial structure for repositories 03, 04 and 05 |
| 11 | Final mascot appearance |
| 12 | Goodbye narration and branded end screen |

The repository cards must display numbers in ascending order:

**01 → 02 → 03 → 04 → 05**

Do not reverse the order.

The narration must not say "Repository number one", "Repository number two", etc.

The card communicates the sequence number visually. The narration begins directly with the repository's actual name.

# 3. OPENING SEQUENCE — EXACT CREATIVE SPECIFICATION

**Target duration: approximately 6–7 seconds.**

The opening is the identity-defining moment of the entire series. It needs to be quick, memorable, attractive and immediately understandable.

## 3.1 First frame — background composition

The video must begin with a visually established background.

Preferred background:

- An actual GitHub repository screen recording or capture.
- Apply approximately 14–18 px Gaussian blur.
- Apply a dark overlay around 65–75% opacity.
- Reduce background contrast and saturation.
- Keep the recognizable GitHub interface visible only as an atmospheric element.
- Do not allow the background to compete with the typography or mascot.

Fallback background:

A premium dark solid background using:

- Base: `#0B0F16`
- Secondary tone: `#111A26`
- Subtle accent: `#17283A`

A low-contrast gradient is allowed. Avoid excessive particles, bright grids, neon effects and artificial lens flares.

**Frame 0000:** Background only. No visible mascot yet.

The screen should already look intentional before the mascot enters.

## 3.2 Mascot entrance

**Entrance point:** Bottom-right corner.

**Animation duration:** Approximately 350–500 milliseconds.

The mascot must enter suddenly, not slowly fade into existence.

Animation:

1. Mascot begins below and slightly outside the visible frame.
2. It moves diagonally upward into the bottom-right region.
3. Opacity increases rapidly.
4. Scale begins around 90–92%.
5. It briefly reaches approximately 102–104% scale.
6. It settles at 100%.
7. It remains still in a neutral standing pose.

Use a short, fast ease-out entrance followed by a controlled settle.

Do not use a cartoon bounce, repeated jumping or exaggerated character animation.

### Mascot entrance audio

Use two coordinated sound layers:

- A short airy rising whoosh.
- A tight, low-impact landing sound.

The impact must occur at the moment the mascot reaches its final position.

## 3.3 Opening typography

Place the main hook on the left side of the composition.

The mascot occupies the right side. The text must remain clearly visible and must not be hidden behind the character.

The typography should feel large, confident and editorial.

The hook:

**"FIVE GITHUB PROJECTS. ONE WORTH YOUR TIME."**

Narration delivery must remain below five seconds.

Display the words as two meaningful groups:

- FIVE GITHUB PROJECTS.
- ONE WORTH YOUR TIME.

The two groups should not appear as a single static sentence.

Use a short directional reveal or controlled scale-pop for the first group. The second group should arrive with slightly stronger emphasis.

The text animation should be coordinated with the spoken words.

### Opening frame layout

| Screen region | Content |
|---|---|
| Left 55% | Main hook typography and captions |
| Right 35% | Mascot |
| Background | Blurred GitHub screen or dark canvas |
| Foreground detail | Small callout, when required |
| Lower safe area | Caption placement if it does not conflict with the main typography |

The mascot should be visually in front of the main background. Text and captions should be positioned in a separate composition region so there is no readability conflict.

## 3.4 "Let's dig in" moment

After the hook:

1. The main hook text clears.
2. The mascot remains momentarily visible.
3. A small callout appears beside the mascot.
4. Callout text: **"LET'S DIG IN."**
5. Narration says the same short line.
6. A subtle interface pop sound accompanies the callout.
7. Mascot exits quickly.
8. The video cuts directly to the first repository card.

Do not add a lengthy explanation here.

## 3.5 Opening frame and sound timeline

| Time | Visual | Sound |
|---|---|---|
| 0.00–0.10s | Background established | Music starts with a restrained opening texture |
| 0.10–0.50s | Mascot enters from bottom-right | Fast airy whoosh |
| 0.40–0.60s | Mascot settles | Short impact |
| 0.55–1.40s | "FIVE GITHUB PROJECTS" appears | Narration starts; subtle text accent |
| 1.40–3.50s | "ONE WORTH YOUR TIME" receives emphasis | Narration continues |
| 3.60–4.50s | Main phrase clears; mascot remains | Music continues |
| 4.20–5.00s | "LET'S DIG IN" callout appears | Narration + UI pop |
| 5.00–5.40s | Mascot exits | Short exit whoosh |
| 5.40–6.40s | Repository 01 card | Card impact |
| 6.40s onward | Hard cut to actual GitHub footage | Repository narration begins |

These are target timings. Actual caption boundaries must follow the final narration audio alignment.

# 4. REPOSITORY INTRODUCTION CARD

Every repository must receive the same recognizable introduction treatment.

**Target duration: approximately one second.**

## Appearance

Use a full-screen dark card.

Design:

- Background: `#0B1018`.
- Main repository title: white.
- Repository number: blue accent.
- Small index label: `01 / 05`.
- Typography: Space Grotesk Bold.
- No unnecessary illustrations.
- No fake GitHub statistics.
- No giant animated logos.

Example structure:

```text
01 / 05

REPOSITORY NAME
```

The actual repository name must be retrieved from the validated repository data.

## Animation

1. Card appears with a direct cut.
2. Large `01` reveals with a quick horizontal movement.
3. Repository name appears with a short masked reveal.
4. A single cinematic impact accent plays.
5. Hold briefly.
6. Cut directly to the actual repository screen recording.

Use a fast scale or position movement, not a complicated transition.

**The narrator must not announce the number.**

The first spoken words after the card must be the actual repository name.

This card template is reused for all five repositories, changing only:

- Repository number.
- Repository name.
- Optional verified owner label.

# 5. REPOSITORY PRESENTATION — MAIN EDITING TEMPLATE

The repository presentation is the main portion of the video.

Each repository should feel like a miniature technical showcase.

The editorial sequence is:

1. Repository introduction.
2. Project purpose.
3. README exploration.
4. Important features.
5. Source-code demonstration.
6. Technical explanation.
7. Short evaluation.
8. Move to the next repository.

The order of the shots may adapt to the actual repository. Do not force a source-code demonstration when the project has no suitable code example or when another visual demonstration is more informative.

## 5.1 Initial repository screen recording

Use authentic GitHub footage.

The first shot should show the repository in a readable desktop layout.

Show:

- Repository owner and name.
- Description.
- Verified stars and forks, when relevant.
- Primary language.
- Other relevant repository information.

Do not invent statistics.

The footage should establish the location of the repository before the camera moves.

### Camera sequence

Start with a stable wide shot.

Then:

- Introduce a gentle push-in.
- Move towards the repository title.
- Focus on the description.
- Hold while narration explains the purpose.
- Pull back or cut into the README section.

Do not zoom for the sake of zooming.

Every camera movement must correspond to the narration or the information on screen.

## 5.2 README exploration

Show the actual README.

Capture the rendered GitHub README using the real repository content.

The camera must perform deliberate scrolling and positioning.

Example shot:

| Phase | Visual behaviour |
|---|---|
| Establish | Show README heading and introduction |
| Reveal | Scroll towards the relevant section |
| Focus | Push towards the important heading |
| Highlight | Highlight the paragraph or feature being discussed |
| Explain | Hold the view during narration |
| Continue | Scroll towards another relevant section |

Use the same process for feature lists, architecture descriptions, installation instructions and other useful content.

Do not scroll continuously at a constant speed.

Use controlled acceleration and deceleration.

## 5.3 Source-code demonstration

When the narration discusses implementation, capture the real source file.

The source recording must display authentic source code.

Use:

- Readable code size.
- Actual file name.
- Relevant syntax highlighting.
- Adequate surrounding context.
- Correct code-line positioning.

The camera may zoom into a function, pan horizontally or move vertically to show its implementation.

Highlight only the actual lines being discussed.

Never invent a highlighted function or make an arbitrary region appear significant.

For code highlights:

- Use a translucent blue selection background.
- Use a thin border.
- Keep opacity moderate.
- Avoid neon glow.
- Do not obscure the underlying code.

The highlight should animate into place, remain during the explanation and disappear after the topic changes.

# 6. MASCOT DESIGN AND ASSET REQUIREMENTS

The mascot artwork will be designed and supplied separately.

The implementation agent must not generate a new mascot design or replace the user's selected character.

The agent must build the overlay system to support the supplied artwork.

## 6.1 Desired mascot appearance

The mascot should have:

- A recognizable and consistent silhouette.
- Clean, polished rendering.
- Consistent proportions.
- Consistent lighting and shading.
- A friendly but neutral expression.
- Clear separation from the background.
- A transparent background.
- No embedded typography.
- No embedded callout.
- No embedded shadow that prevents flexible compositing.

The character should look like a consistent presenter throughout the episode.

## 6.2 Required neutral assets

Request the following asset variations:

| Asset name | Purpose |
|---|---|
| `mascot_front_neutral.png` | Opening and general front-facing appearance |
| `mascot_left_neutral.png` | Left-oriented composition |
| `mascot_right_neutral.png` | Right-oriented composition |
| `mascot_threequarter_left.png` | Optional alternate direction |
| `mascot_threequarter_right.png` | Optional alternate direction |

Preferred format: transparent RGBA PNG.

Recommended artwork canvas: approximately 1024 × 1536 or higher, with sufficient transparent margins.

The character should remain completely inside the artwork canvas. Do not crop hands, feet or the head.

Use separate left/right orientations when the character contains asymmetric accessories, markings or clothing. Do not mirror these details accidentally.

## 6.3 Mascot behaviour

The mascot is a recurring visual presenter, not an animated actor.

Allowed behaviour:

- Entering from a screen edge.
- Short scale and position entrance.
- Small controlled settling movement.
- Remaining still while a callout is visible.
- Exiting the screen.
- Reappearing in a different screen region.
- Switching between the supplied neutral orientations.

Do not introduce:

- Pointing gestures.
- Thumbs-up gestures.
- Disagreement gestures.
- Surprised expressions.
- Fake talking animations.
- Unrequested waving.
- Gestures that imply the character is reacting to or endorsing the project's claims.

The mascot must not communicate an opinion or reaction that is not present in the narration.

## 6.4 Mascot positions

The mascot should not remain in the same corner for the entire video.

Use these position presets:

| Position | Screen region |
|---|---|
| A | Bottom-right |
| B | Bottom-left |
| C | Right-middle |
| D | Left-middle |

The exact coordinates should be configurable.

Use approximately 30–45% of frame height, depending on the pose and available space.

Maintain a margin of approximately 60–80 pixels from the canvas boundaries.

Position selection must be based on available negative space in the actual captured footage.

Never place the mascot over:

- Important code.
- Repository titles.
- Important buttons.
- Highlighted lines.
- Critical README text.
- Caption text.

## 6.5 Recurrence and placement

Use the following as a starting placement pattern:

- Opening: bottom-right.
- Repository 01: bottom-right initially, then left-side reappearance.
- Repository 02: bottom-left initially, then right-side reappearance.
- Repository 03: right-middle or left-middle depending on available space.
- Repository 04: opposite-side placement from the preceding segment.
- Repository 05: a composition chosen from the available negative space.
- Closing: front-facing neutral appearance.

These are not mandatory fixed positions if the footage makes them unsuitable.

The essential rule is that the mascot changes position naturally while remaining unobtrusive.

A repository section should generally contain no more than two or three mascot appearances.

Do not keep the mascot permanently visible.

## 6.6 Mascot callouts

Callouts should be short and useful.

Examples:

- "Lightweight architecture"
- "Interesting implementation"
- "Built for developers"
- "Modular design"
- "Open-source tooling"

These are examples only. The actual wording must be supported by repository facts and narration.

Visual design:

- Rounded dark panel.
- Background: `#111A26`.
- Text: `#F5F7FA`.
- Thin subtle border.
- Small blue accent.
- Rounded corners.
- Optional small pointer towards mascot.
- No excessive glow.

Callout animation:

1. Scale from approximately 88% to 100%.
2. Quick ease-out.
3. Text fades in with a short delay.
4. Hold while the narration explains the point.
5. Exit using a quick fade and scale-down.

Callouts must never simply repeat a full narration sentence.

# 7. CAPTION SYSTEM — HIGH PRIORITY

The caption system is a core part of the creative identity.

Do not implement ordinary static subtitles as the only caption style.

The desired style is modern social-media kinetic typography adapted for landscape video.

Captions must help viewers understand the narration while maintaining attention.

## 7.1 Caption philosophy

Split narration into meaningful phrase groups.

Typical group size:

- Two to five words.
- Sometimes a single important word.
- Maximum two lines in most situations.

Do not display every sentence as one long paragraph.

Do not randomly display words with no relationship to the spoken meaning.

Preserve the complete spoken meaning through successive caption groups. Selective emphasis means selective visual treatment, not removal of important information.

## 7.2 Example

Narration:

"This project provides developers with a lightweight framework for building scalable applications."

Possible caption sequence:

```text
A LIGHTWEIGHT
FRAMEWORK

BUILT FOR
DEVELOPERS

SCALABLE
APPLICATIONS
```

The final caption grouping and duration must follow the actual narration.

## 7.3 Font specification

Primary display and caption font:

**Space Grotesk**

Weights:

- 600 — regular emphasis.
- 700 — strong emphasis.

Secondary information:

**IBM Plex Sans**

Technical labels and small code-related annotations:

**IBM Plex Mono**

Do not introduce a large collection of unrelated fonts.

Use a consistent font hierarchy throughout the entire episode.

## 7.4 Caption typography

At 1920 × 1080:

| Property | Recommended value |
|---|---|
| Main phrase font size | 56–72 px |
| Strong single-word emphasis | 80–108 px |
| Small supporting caption | 42–52 px |
| Weight | 600–700 |
| Line height | 0.95–1.1 |
| Maximum lines | Usually 2 |
| Side safe margin | 100 px |
| Bottom safe margin | 100 px |

Sizes may be adjusted for the length of the phrase.

Do not shrink a long sentence until it becomes difficult to read. Split it into additional meaningful groups.

## 7.5 Caption colours

Use this consistent palette:

| Purpose | Colour |
|---|---|
| Primary text | `#F5F7FA` |
| Main accent | `#63B8F2` |
| Secondary emphasis | `#FFD166` |
| Background panel | `#101722` |
| Subtle border | `#334155` |
| Supporting text | `#AAB6C5` |

Blue is the primary accent.

Yellow should be reserved for occasional high-value emphasis.

Do not turn every caption word into a different colour.

Avoid excessive red, green, neon colours and rainbow typography.

## 7.6 Caption backgrounds

Three caption treatments may be used.

**Style A — Floating typography**

Text directly over the video with a controlled shadow or subtle dark backing.

**Style B — Rounded caption panel**

A dark translucent panel with clean typography.

**Style C — Highlighted word**

A selected word receives a blue or yellow background, or a contrasting text colour.

Do not use a solid rectangular background for every caption.

Choose the treatment according to footage contrast.

## 7.7 Caption animation library

Implement reusable animation presets.

| Preset | Behaviour | Appropriate use |
|---|---|---|
| `caption-static-focus` | Phrase appears; active word changes colour | Normal narration |
| `caption-pop` | Controlled scale-up | Important keywords |
| `caption-slide-up` | Phrase enters from below | New explanation |
| `caption-slide-side` | Text enters laterally | Section progression |
| `caption-mask-reveal` | Text revealed through a clipping mask | Important phrase |
| `caption-stack` | Two-line stacked phrase | Technical explanation |
| `caption-highlight-bar` | Background bar moves behind text | Feature emphasis |
| `caption-single-word` | Large isolated keyword | Strong editorial moment |

## 7.8 Preventing repetitive caption animation

This is mandatory.

Do not use scale-up for every caption.

Suggested distribution:

- 55% static or lightly animated phrase captions.
- 20% directional slide or fade.
- 15% controlled scale-pop.
- 10% masked or highlighted reveal.

These are approximate creative targets, not rigid statistical limits.

Use no more than one strong caption impact animation within a short passage unless the narration has a genuine reason for additional emphasis.

Some captions should remain almost still while the camera moves.

This contrast makes the animated moments more meaningful.

## 7.9 Word timing

Caption timing must use actual narration alignment.

Do not estimate the time of every word using average syllable duration when accurate word alignment is available.

Build the caption pipeline in three independent stages:

1. Speech transcript and word timestamps.
2. Phrase grouping and emphasis selection.
3. Visual caption rendering and animation.

The caption renderer must be replaceable without regenerating the narration.

Technical terms, repository names, package names and code identifiers must be spelled correctly.

Do not visually emphasize a technical term if the transcription is uncertain.

## 7.10 Caption-camera coordination

The camera and caption tracks must be independent but coordinated.

Examples:

- Camera pushes towards repository description while captions occupy the lower safe area.
- Camera moves towards the README feature section while the phrase caption appears in an available region.
- Camera zooms towards a code function while captions remain in a clear, non-obstructive area.
- A strong technical keyword can briefly receive a larger caption treatment, but it must not cover the implementation being explained.

**Never repeatedly zoom the whole video towards the caption.**

# 8. CAMERA MOVEMENT AND KEYFRAME SPECIFICATION

The video must use purposeful camera movement.

Camera movements should make the viewer look at the relevant subject.

They must not feel like random zooming.

## 8.1 Supported camera operations

Implement these reusable camera properties:

- Position X.
- Position Y.
- Scale.
- Optional rotation, used sparingly.
- Opacity where appropriate.
- Easing curve.
- Shot start and end frame.

Support:

- Smooth push-in.
- Smooth pull-back.
- Horizontal pan.
- Vertical pan.
- Controlled scroll.
- Short snap zoom.
- Static hold.

All camera operations must be keyframe-driven.

## 8.2 Keyframe interpolation

Use:

- Cubic ease-in-out for smooth camera moves.
- Ease-out for entrance movements.
- Ease-in for exits.
- Linear movement for deliberately controlled scrolling only where appropriate.

Do not use abrupt linear movement for every camera animation.

The animation engine should support configurable cubic Bézier curves.

## 8.3 Camera examples

**Repository overview**

- Frame begins at 100% scale.
- Gradually increases to 106–108%.
- Focuses on repository information.
- Holds while narration explains.
- Returns to a wider composition before changing subjects.

**README**

- Start with a readable section.
- Scroll to the important heading.
- Push in slightly.
- Hold the relevant content.
- Move to the next section only after narration progresses.

**Source code**

- Begin with the complete file or a readable context.
- Move towards the actual target function.
- Zoom to the relevant lines.
- Highlight the lines.
- Hold during explanation.
- Move away or cut to the next shot.

## 8.4 No repetitive zoom pattern

Vary camera movement according to the content.

Do not apply the same push-in to every sentence.

Use a mixture of:

- Wide static shots.
- Short push-ins.
- Longer slow zooms.
- Horizontal movement.
- Vertical movement.
- Direct cuts between distinct content sections.
- Static holds during detailed explanations.

The viewer must have time to read the content.

Do not move the camera while the important code is difficult to follow.

## 8.5 Camera movement over captions

A caption does not automatically trigger a camera zoom.

Zoom into the visual subject, not the subtitle.

A caption can receive a small scale animation independently while the repository footage remains stable.

Reserve full-frame caption-focused camera movement for a small number of especially important hook or emphasis moments.

# 9. TRANSITION POLICY — HARD CUTS FIRST

The default transition is a direct cut.

Do not use decorative transition effects between every shot.

Preferred editing techniques:

- Direct hard cut.
- Cut on narration beat.
- Cut on music beat.
- Cut on mascot exit.
- Cut from card directly into repository footage.
- Cut from one relevant website state into another.
- Cut when the narration moves to a new topic.

Avoid:

- Repeated zoom transitions.
- Constant whip pans.
- Spinning transitions.
- Flash transitions.
- Glitch transitions.
- Unnecessary page-turn effects.
- Repeated particle transitions.

A transition effect may only be added when it has a clear editorial purpose.

The repository card already acts as a visual separator between repositories.

Sound design must be part of the editing pipeline, not added randomly at the end.

The video needs a recognizable sound identity.

Use short, polished, modern effects.

Avoid cartoon sound effects, meme sounds, overused gaming effects and excessively loud cinematic booms.

Download short effects that can be edited precisely.

Avoid long effects when a 150–500 ms sound will do the job.

## 10.3 Sound-effect placement rules

**Mascot entrance**

Whoosh begins slightly before the visual entrance. Impact coincides with the mascot settling.

**Mascot exit**

Use a short outgoing whoosh. Do not use a large impact on an exit.

**Callout**

Play the pop precisely when the callout becomes visible.

**Caption**

Use caption sound accents selectively. Do not play a click for every spoken word.

**Repository card**

Use one recognisable card impact per repository. The sound should identify the recurring card pattern.

**Camera push**

Use a soft rising movement only for selected pushes. Not every zoom needs a sound.

**Code highlight**

Use a subtle interface sound at the moment the highlight appears. Keep it quieter than the narration.

**Goodbye**

Use a restrained closing sound and a smooth music fade.

## 10.4 Audio mixing

The narration always takes priority.

Suggested mixing starting points:

- Narration: clear, centered and intelligible.
- Music: approximately 10–14 dB lower than the narration in perceived level during speech.
- Important sound effects: audible but never masking words.
- Minor interface accents: subtle.
- Transient impacts: short and controlled.

Use automatic music ducking linked to narration activity.

The music must remain continuous across repository boundaries.

Do not restart the music at every card.

Avoid audio clipping.

Use loudness metering and a final true-peak check. A reasonable initial delivery target is around -14 LUFS integrated and no higher than -1 dBTP, subject to listening checks and the intended publishing platform.

# 11. BACKGROUND MUSIC

Use one consistent instrumental background track across the episode.

Preferred musical character:

- Modern technology documentary.
- Minimal electronic.
- Light cinematic pulse.
- Subtle rhythmic movement.
- No distracting vocals.
- No aggressive drums.
- No melody that competes with narration.

The track should create forward movement without making the video feel like an action trailer.

Music structure:

- Opening: slightly energetic.
- Repository sections: controlled and consistent.
- Important moments: subtle intensity increase where appropriate.
- Technical explanation: lower musical energy.
- Closing: natural fade-out.

If a suitable licensed track is not available, use a temporary placeholder during development. Do not delay implementation of the visual pipeline waiting for a final music selection.

# 12. REPOSITORY-TO-REPOSITORY REPEATABLE TEMPLATE

All five repositories must use the same editorial structure.

For every repository:

### A. Introduction card

- Number and exact repository name.
- One-second target duration.

# 16. IMPLEMENTATION ARCHITECTURE

Do not implement this as a collection of hardcoded screenshots with separately coded animations.

Build a reusable Long-form composition system.

The system should be driven by a master timeline and structured scene data.

## 16.1 Required independent tracks

Implement the following logical tracks:

| Track | Responsibility |
|---|---|
| BackgroundTrack | Opening and other background layers |
| ScreenRecordingTrack | Authentic GitHub website footage |
| CameraTrack | Zoom, pan, scroll and framing |
| HighlightTrack | README, repository and source-code highlights |
| MascotTrack | Mascot asset, position, orientation and animation |
| CalloutTrack | Short presenter callouts |
| TitleTrack | Opening titles and repository cards |
| CaptionTrack | Phrase-based and word-synchronized captions |
| NarrationTrack | Main spoken narration |
| MusicTrack | Continuous instrumental music |
| SfxTrack | Event-driven sound effects |

The tracks must share one master timeline.

No track should independently reset its clock at a repository boundary.

## 16.2 Keyframe data model

Use frame-based timing for visual animations.

An illustrative structure:

```ts
interface Keyframe<T> {
  frame: number;
  value: T;
  easing:
    | "linear"
    | "ease-in"
    | "ease-out"
    | "ease-in-out";
}

interface TransformState {
  x: number;
  y: number;
  scale: number;
  opacity: number;
}

interface MascotOverlay {
  asset: string;
  position: "bottom-right"
    | "bottom-left"
    | "right-middle"
    | "left-middle";
  startFrame: number;
  endFrame: number;
  transform: Keyframe<TransformState>[];
  calloutId?: string;
}

interface CaptionCue {
  text: string;
  startFrame: number;
  endFrame: number;
  style: string;
  emphasisWords: string[];
  animation: string;
}

interface AudioCue {
  asset: string;
  startFrame: number;
  gainDb: number;
  fadeInFrames?: number;
  fadeOutFrames?: number;
}
```

This is a conceptual contract. Adapt names and types to the current project architecture rather than blindly duplicating existing systems.

The timeline must support deterministic rendering.

## 16.3 Scene configuration

A repository should be configured using data, not separate renderer code.

For example:

```ts
interface RepositoryScene {
  repositoryId: string;
  sequenceNumber: number;
  repositoryName: string;

  narration: {
    audioAsset: string;
    transcript: string;
  };

  captures: {
    repositoryPage?: string;
    readme?: string;
    sourceFiles?: string[];
  };

  shots: ShotPlan[];
  captions: CaptionCue[];
  mascotOverlays: MascotOverlay[];
  soundEffects: AudioCue[];
}
```

The same scene renderer should handle all five repositories.

It should change the content and shot plan without changing the fundamental visual identity.

## 16.4 Rendering architecture

Use the existing project infrastructure where it is suitable.

Preferred architecture:

- Chromium/CDP for authentic GitHub page capture.
- Existing script-generation and validation infrastructure.
- Existing Groq LLM integration.
- Existing Kokoro ONNX TTS infrastructure.
- Existing word-alignment functionality where reliable.
- A compositor for animated layers and camera movement.
- FFmpeg for final encoding and audio composition.

Do not introduce unnecessary AI services or paid APIs.

Do not build a new Python-based editing pipeline if the current TypeScript/Rust architecture can support the work.

## 16.5 Rendering performance

A five-minute video at 30 FPS contains approximately 9,000 frames.

Do not implement a strategy that launches Chromium and takes a new screenshot for every output frame.

That approach is unnecessarily expensive and can make rendering impractically slow.

Instead:

1. Capture genuine GitHub page states and required footage.
2. Capture the source-code and README material.
3. Store shot geometry and target locations.
4. Animate camera transforms, highlights, captions and mascot overlays in the compositor.
5. Use FFmpeg to assemble and encode the final composition.
6. Benchmark the actual renderer on representative scenes before deciding on a more expensive frame-generation strategy.

Use caching where it improves deterministic rendering without compromising authenticity.
